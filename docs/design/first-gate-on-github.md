# What the first gate on GitHub showed, and what changes

- **Phase and date:** Phase 12, the live test on HealthQCopilot, stages 3a to 6; 2026-11-27 (UTC)
- **Upstream and reference:** github/spec-kit `v1.4.3`; `imatiqul/azure-ai-cloud-healthcare`, pull requests 84 to 88, with the kit at `ce58712` installed; the kit's own pull request 6
- **Requirement IDs covered:** FGR-1 to FGR-15, new with this document. Five say in the documents what the live test found out about GitHub. Ten make a command, a check, a page or the kit's own pipeline do what the live test showed they should. No gate rule changes
- **Assumptions:**
  1. The owner said on 2026-11-26 that each failure of the live test is reported as it is and fixed on a local branch of the kit, which he pushes.
  2. A review by a program is a reader's findings. GitHub Copilot's four findings on pull request 86 were each checked against the code before anything changed.
  3. What GitHub does with a run that its own token caused is read from what happened in HealthQCopilot, and from GitHub's page on triggering a workflow (source 2). That page names the events that still start a run; `workflow_run` is not among them.
- **Unverified:** nothing here has run on GitHub. FGR-2 reads the rules of the default branch with the request that `CK-ENFORCE-SETUP` already makes there; the field it reads, `dismiss_stale_reviews_on_push`, is the one HealthQCopilot's rules hold. FGR-10 takes GitHub's words for an unknown commit from one answer, given in this workspace on 2026-11-27

## What happened

The kit was brought into HealthQCopilot as it stands on its `main` (pull request 86). Then G1 and G2 of spec 020 were reviewed on a pull request that the kit's workflow `agentic-open-pull-request` opened as `github-actions[bot]` (pull request 87). The owner approved them in a review that carried the two lines `gate` printed. `record --change pull/87` read that review from GitHub and wrote the two decision records: the first of that repository.

The records went onto pull request 87 as one more commit. That repository's rule for `main` dismisses an approval when a commit is pushed, and GitHub dismissed the review that the records cite. The pipeline said so, in `CK-APPROVER`: "the review state is DISMISSED, not APPROVED". The owner approved again with the same lines and merged. The records were then written again from the review that stands, on a branch of their own made after the merge, and a pull request opened by the same workflow (88). There the pipeline, running as `github-actions[bot]`, passed `CK-APPROVER` and `CK-GATE-MIRROR` for both records. It is the first gate that a review on GitHub passed and the pipeline judged.

- **AC-001** (verifies FGR-1): Then `docs/install.md`, `extensions/agentic/commands/gate.md`, `docs/limits.md` and `ci/github-actions.yml` each say that a commit pushed onto the pull request dismisses the review where approvals are dismissed on a push, and name open question 1's two ways or point to the place that does.
- **AC-002** (verifies FGR-2): Given a stand-in that says approvals are dismissed on a push and a pull request that is open with a review carrying the gate's line, When `record --change` runs, Then the record is written and the output names the review and says that a push onto the pull request dismisses it. ## Open question

1. **How the kit records a gate decision where approvals are dismissed on a push.** One way: the record is committed after the merge, on a branch of its own, as stage 5 of the live test did, and the mirror job runs after the push to the default branch and opens the records' pull request. Until the records are merged, the gate shows as open; for a change whose plan or code needs that gate, `CK-GATE-RECORD` fails on the default branch in that time. The other: the record stays on the pull request, and `CK-APPROVER` and `CK-GATE-MIRROR` accept a later approval by the same person, with the same line, for the same evidence, in place of the review the record cites, as the owner gave at 02:27 UTC; each reviewer then approves twice. Yours to decide. Nothing in this change prejudges it: FGR-1 and FGR-2 only say what happens. **Answered on 2026-11-28:** the owner said that both can be accepted. `docs/design/both-ways-to-record.md` (BWR-1 to BWR-8) has how the kit now takes either.

## What this does not do

- It does not change how the kit records a gate, nor the mirror job. That waited for open question 1, which `docs/design/both-ways-to-record.md` answers.
- It does not report which failures a change brings and which its base already has (row 15). That needs a design of its own: running every check twice, and saying what a failure on the base means for the change.
- It does not make the connect workflow run for a pull request that the bot opened. GitHub decides that.
- It does not map the id of a bypass actor to a repository role.
- It does not answer GitHub Copilot's review on GitHub. Whether its threads are answered there is the owner's to say.
